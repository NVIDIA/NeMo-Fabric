The NVIDIA NeMo Fabric `nvidia.fabric.hermes` adapter runs Hermes Agent through
its Python SDK. The adapter maps normalized NeMo Fabric configuration into
Hermes Agent models, tools, skills, Model Context Protocol (MCP) servers,
sessions, and Relay telemetry.

## Install the Adapter

The adapter package supports Python 3.11 through 3.14. Use [Hermes Agent v0.22.5](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.5) with Python 3.14. This release includes dependency security fixes absent from v2026.9.24 and supports Relay telemetry and streaming. Hermes Agent 0.20 and later is not installable from PyPI. Follow the [Hermes Agent installation guide](https://hermes-agent.nousresearch.com/docs/installation) and select v0.22.5.

Install the NeMo Fabric runtime and bare Hermes adapter into the Python
environment that runs Hermes Agent:

```bash
pip install "nemo-fabric[hermes-agent]"
```

These packages do not install Hermes Agent. If a different environment runs
NeMo Fabric, install only the bare adapter in the Hermes Agent environment:

```bash
python -m pip install nemo-fabric-adapters-hermes
```

The adapter's `relay` and `full` extras install `nemo-relay>=0.10,<0.11`. Install Hermes Agent separately in the same environment. Keep that environment separate from applications that use Relay 0.11 for other NeMo Fabric adapters. The adapter reports a compatibility error at startup if Relay telemetry is enabled with an unsupported Hermes or Relay installation.

For local NeMo Fabric development, run the following command from the repository root. The recipe checks out Hermes Agent v0.22.5 at commit `bf0203a794a07aac3ff764972ab9087baa4e4f4e` and creates an isolated Python 3.14 environment with the adapter's `relay` extra. Hermes declares its Python package version as `0.0.0`; use the Git tag and commit to identify the release when reviewing scanner results.

```bash
just install-hermes-agent
export ADAPTER_PYTHON="$PWD/.venv-hermes/bin/python"
```

For separate environments, set `ADAPTER_PYTHON` in the runtime environment to
the adapter environment's Python interpreter. Use
matching NeMo Fabric release versions for the runtime and adapter package
unless a different pairing has been explicitly validated.

## Configure the Adapter

Select the Hermes Agent harness integration in `HarnessConfig`:

```python
from nemo_fabric import HarnessConfig

harness = HarnessConfig(adapter_id="nvidia.fabric.hermes")
```

Use normalized `FabricConfig` fields to configure the model, workspace, skills,
MCP servers, replacement system instructions, turn limit, and native tool
selectors, and telemetry. The adapter rejects `append` system instructions.

During run-plan resolution, NeMo Fabric Core validates the
`models.<role>.top_p` (from 0 through 1) and positive
`models.<role>.max_tokens` fields against the Hermes descriptor before
runtime startup. Hermes reads these prevalidated values from `AgentConfig`. A
model-level `max_tokens` overrides the harness-level default for the selected
model role.

The Hermes descriptor validates the following `harness.settings` fields:

| Setting | Type | Default | Description |
| --- | --- | --- | --- |
| `reasoning_config` | object | `{"effort": "none"}` | Configures Hermes model reasoning. The closed object accepts an optional `enabled` boolean and an optional `effort` value of `none`, `minimal`, `low`, `medium`, `high`, or `xhigh`. |
| `plugins_enabled` | array of nonempty strings | `[]` | Enables Hermes plugins by identifier. Relay telemetry uses the generated `plugins.toml`; do not list the removed `observability/nemo_relay` plugin. |
| `save_trajectories` | boolean | `false` | Enables Hermes-native JSONL conversation trajectory saving. This is separate from normalized NeMo Fabric telemetry. |
| `max_tokens` | positive integer | `512` | Limits the number of tokens in each Hermes model response. |
| `terminal_timeout` | positive number | `60` | Limits a Hermes terminal operation in seconds. |

For example:

```python
from nemo_fabric import HarnessConfig

harness = HarnessConfig(
    adapter_id="nvidia.fabric.hermes",
    settings={
        "reasoning_config": {"enabled": True, "effort": "medium"},
        "plugins_enabled": ["disk-cleanup"],
        "save_trajectories": True,
        "max_tokens": 1024,
        "terminal_timeout": 90,
    },
)
```

Use `runtime.max_turns` to set the Hermes agent-loop budget. The adapter maps
that normalized field to `AIAgent.max_iterations`; `max_iterations` is not a
Hermes harness setting.

## Understand the Runtime Lifecycle

Each NeMo Fabric runtime creates one Hermes Agent `AIAgent` and one `SessionDB`.
Ordered invocations reuse those objects and the conversation history until the
runtime stops. The adapter finalizes and flushes Relay subscriber output after
each invocation so ATOF and ATIF artifacts are complete when it returns.

With a live Relay runtime, Hermes emits `compaction` when a tracked compaction
rewrites history or provider state. It emits `compaction.attempt` when the
attempt is blocked, skipped, fails, or aborts without a rewrite.

For the complete configuration and lifecycle reference, refer to the
[Hermes Agent adapter guide](https://github.com/NVIDIA/NeMo-Fabric/tree/main/adapters/python/hermes).

## Serve the API Server and Dashboard

A runtime can serve Hermes's API server and dashboard as child processes
alongside its embedded agent:

```python
from nemo_fabric import HarnessConfig

harness = HarnessConfig(
    adapter_id="nvidia.fabric.hermes",
    settings={"interfaces": {"api": {"port": 8642}, "dashboard": {"port": 9119}}},
)
```

- The adapter starts `python -m hermes_cli.main gateway run` for the API server
  and `python -m hermes_cli.main dashboard --skip-build --isolated`, on the
  adapter's interpreter and the runtime's Hermes home, each on `127.0.0.1` at
  its port. Each must pass its health check, `GET /health` or
  `GET /api/status`, within `startup_timeout_seconds` (60 by default, at most
  75) of the runtime's start. `start` fails if a port is in use or a child exits first; a failed
  start stops the children it started and leaves no token. Set `enabled` to
  `false` to keep a configured interface off.
- The children inherit the adapter host's environment without its
  `API_SERVER_*` variables. The gateway also starts any other Hermes platform
  that this environment configures, such as Telegram with `TELEGRAM_BOT_TOKEN`
  or webhooks with `WEBHOOK_ENABLED`.
- Once every enabled interface passes, the adapter writes the API server's
  bearer token, generated at each start, to
  `<artifact root>/.fabric/hermes/runtimes/<runtime-id>/interfaces/api.token`
  with mode `0600`. Send it as `Authorization: Bearer <token>`. Only the
  gateway child receives it. Processes that run as the runtime's user,
  including the agent's own tools, can read it.
- The dashboard has no sign-in. On loopback, Hermes embeds its session token in
  the page, so anyone who can reach the port can use the dashboard and its
  browser chat, which runs the agent. The adapter turns off none of its pages.
  Browser chat needs Hermes's built terminal UI bundle.
- With interfaces enabled, the adapter writes an `openai` or `custom` model
  that has a `base_url` to `config.yaml` as Hermes's `custom` provider, with
  its key as a reference to `api_key_env`, so the API server and browser chat
  use the configured endpoint and key.
- Managed children launch through an adapter-owned bootstrap that applies Fabric's instructions, enabled/blocked toolsets, turn limit, generation settings, and trajectory setting when native Hermes agent instances are constructed. Fabric-owned settings take precedence over native constructor defaults and instruction overrides. Native provider routing and session identity remain unchanged. The bootstrap reads an owner-only `interfaces/agent-config.json` snapshot, removed on stop, because Hermes v0.22.5's API constructor does not read all these settings from `config.yaml`. Independently started gateways bypass the bootstrap.
- `stop` removes the token, sends SIGTERM to each child's process group, and
  SIGKILL to what remains after 5 seconds. The gateway drains in-flight API
  runs and cron jobs for 3 seconds. After start, a child that exits doesn't fail
  the runtime check, and NeMo Fabric doesn't restart it.
- The embedded agent, the gateway, the dashboard and browser chat share the
  Hermes home, and Hermes coordinates their writes. The dashboard's gateway
  actions, such as restart, start Hermes processes outside the runtime.
- The API server needs `aiohttp`, from Hermes's `messaging` extra. The dashboard
  needs a built frontend at `HERMES_WEB_DIST` or Hermes's own
  `hermes_cli/web_dist`; the adapter never builds it. Interfaces need a POSIX
  host: on Windows, `start` fails with `hermes_interfaces_unsupported_platform`
  before any child starts.

## Runtime Health

`Fabric.check()` supports `live`, `active`, and `ready`. The adapter checks native agent and database ownership, the initialized invocation interface, and a fresh `get_activity_summary()` diagnostic response.

Refer to the [SDK health-check overview](../../sdk/health-checks.mdx) for shared behavior and a comparison of native evidence across adapters.
