The NVIDIA NeMo Fabric `nvidia.fabric.hermes` adapter runs Hermes Agent through its Python SDK. It maps normalized configuration into an embedded agent, reuses its conversation across ordered invocations, and returns normalized results and telemetry references.

For native API and browser access, invocation-path diagrams, and shared configuration behavior, see [Hermes native interfaces](./hermes-interfaces.mdx).

## Install the Adapter

Use [Hermes Agent v0.22.5](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.5) with Python 3.14. The adapter package supports Python 3.11 through 3.14, but Hermes Agent must be installed separately from source; versions 0.20 and later are not available from PyPI. Follow the [Hermes Agent installation guide](https://hermes-agent.nousresearch.com/docs/installation) and select v0.22.5.

Install the runtime and adapter in the environment that runs Hermes:

```bash
python -m pip install "nemo-fabric[hermes-agent]"
```

If the application runs NeMo Fabric in a separate environment, install `nemo-fabric-adapters-hermes` in the Hermes environment and set `ADAPTER_PYTHON` in the application's environment to that interpreter. Use matching runtime and adapter release versions unless a different pairing has been validated.

For Relay, install the adapter's `relay` extra in the Hermes environment. It requires `nemo-relay>=0.10,<0.11`; keep this environment separate from applications using Relay 0.11 for other adapters. Startup rejects unsupported Hermes/Relay combinations.

For repository development, the following recipe checks out v0.22.5 at `bf0203a794a07aac3ff764972ab9087baa4e4f4e` and prepares an isolated Python 3.14 environment with Relay support:

```bash
just install-hermes-agent
export ADAPTER_PYTHON="$PWD/.venv-hermes/bin/python"
```

The installer preserves local checkout changes and stops rather than overwriting them. Set `HERMES_AGENT_CHECKOUT` to a separate clean checkout or a new directory to install without changing `external/hermes-agent`; the target environment remains `.venv-hermes`.

Hermes reports its Python package version as `0.0.0`, so use its Git tag and commit to identify the installed release. The pinned release includes dependency security fixes absent from v2026.9.24.

## Configure the Adapter

Use normalized `FabricConfig` fields for the model, instructions, tools, skills, MCP servers, workspace, turn limit, and telemetry. Use `harness.settings` for Hermes-specific options and native interface selection.

The following example configures an embedded SDK agent with file tools:

```python
from nemo_fabric import FabricConfig

config = FabricConfig.from_mapping(
    {
        "metadata": {"name": "hermes-agent"},
        "harness": {
            "adapter_id": "nvidia.fabric.hermes",
        },
        "models": {
            "default": {
                "provider": "openai",
                "model": "your-model",
                "base_url": "https://MODEL_HOST/v1",
                "api_key_env": "MODEL_API_KEY",
                "temperature": 0.0,
                "top_p": 0.9,
                "max_tokens": 1024,
            }
        },
        "instructions": {
            "system": {"mode": "replace", "content": "Help with files in the workspace."}
        },
        "tools": {"enabled": ["file"], "blocked": ["terminal"]},
        "runtime": {"max_turns": 8},
        "environment": {"provider": "local", "workspace": "."},
    }
)
```

Replace the endpoint and model, and provide `MODEL_API_KEY` in the adapter environment before starting. To add native API or browser access, follow the [Hermes native interfaces guide](./hermes-interfaces.mdx).

The adapter supports `instructions.system.mode: replace` and rejects `append`. Tool selectors are Hermes toolset names. `models.<role>.top_p` must be between 0 and 1, and `max_tokens` must be positive. A model-level token limit takes precedence over `harness.settings.max_tokens`. If both are omitted, the adapter passes `None` to preserve Hermes' native response token limit behavior for embedded and native interface agents. Use `runtime.max_turns`, not a `max_iterations` harness setting, to control the agent loop.

Each `skills.paths` entry is a skill or a folder of skills. An entry that contains `SKILL.md` is one skill. Otherwise each folder directly inside the entry that contains `SKILL.md` is a skill, and other files and folders are ignored. Mix the two forms to combine a shared folder of skills with a skill mounted on its own. An entry that exists but holds no skills, such as a new, empty volume, loads nothing. Start fails with `hermes_skill_not_found` when an entry does not exist and with `hermes_skill_invalid` when an entry is not a folder or two skills share a name; the error names the entry or both skill folders. The adapter passes each skill folder to Hermes Agent's `skills.external_dirs`, so Hermes does not search the rest of a configured folder.

### Hermes Settings

The descriptor uses closed schemas, so unknown settings are rejected.

| Setting | Default | Behavior |
| --- | --- | --- |
| `reasoning_config` | `{"effort": "none"}` | Optional `enabled` boolean and `effort`: `none`, `minimal`, `low`, `medium`, `high`, or `xhigh`. |
| `plugins_enabled` | `[]` | List of nonempty native plugin identifiers. Relay uses its generated plugin configuration; do not list the removed `observability/nemo_relay` plugin. |
| `save_trajectories` | `false` | Save native JSONL trajectories; separate from normalized telemetry. |
| `max_tokens` | Hermes native (`None`) | Positive response-token limit when the selected model has no limit. |
| `terminal_timeout` | `60` | Positive timeout in seconds for a Hermes terminal tool operation; this does not enable a TUI. |

Native interface settings are documented in the [Hermes native interfaces guide](./hermes-interfaces.mdx#enable-native-interfaces).

By default, the Hermes home is
`<artifact root>/.fabric/hermes/runtimes/<runtime_id>`, so runtimes don't share
config or the session database. With `runtime.keep_state`, it is the agent's
state folder, `<artifact root>/.fabric/state/nvidia.fabric.hermes/<agent name>`:
every runtime of the agent then uses the same session database, memory, skills
and logs. Each runtime starts a new session, and earlier sessions stay in the
database. At each start, the adapter rewrites `config.yaml` and removes an
API token that an earlier runtime left in the Hermes home.

## Understand the Runtime Lifecycle

Each runtime creates one embedded Hermes `AIAgent` and one `SessionDB`. Ordered SDK invocations reuse these objects and their conversation history until stop closes them. The Hermes home is stored under `<artifact root>/.fabric/hermes/runtimes/<runtime-id>`, or in the agent's state folder with `runtime.keep_state`; retaining files does not by itself establish cross-runtime conversation resume.

SDK invocations return normalized NeMo Fabric `RunResult` objects. The adapter finalizes the Hermes Relay session and flushes subscribers before returning, so available ATOF/ATIF artifacts are complete at that invocation boundary. Native interface responses follow a different path, described in [What NeMo Fabric Normalizes](./hermes-interfaces.mdx#what-nemo-fabric-normalizes).

## Runtime Health

`Fabric.check()` supports `live`, `active`, and `ready`. It checks the embedded agent's session/database ownership, invocation interface, and a fresh `get_activity_summary()` diagnostic response. These checks do not establish native interface-child health after startup.

Refer to the [SDK health-check overview](../../sdk/health-checks.mdx) and the [Hermes adapter reference](https://github.com/NVIDIA/NeMo-Fabric/tree/main/adapters/python/hermes) for additional details.
