Use `nemo_fabric.integrations.harbor:FabricAgent` when Harbor should own task
materialization, environments, verification, rewards, and retries while NeMo Fabric
selects and runs the agent harness.

One Harbor trial consumes one complete NeMo Fabric config. Compare harnesses or
capability variants by holding the Harbor task and verifier fixed and starting
a separate run with a different config or explicit Harbor skill/MCP input.
The checked-in Harbor workflows qualify Hermes Agent, Claude, and the
NVIDIA-labs Object Oriented Agents (NOOA) `BenchAgent` end to end.

Refer to the repository examples for installation and runnable Harbor
workflows:

[Run NeMo Fabric agents with Harbor](https://github.com/NVIDIA/NeMo-Fabric/tree/main/examples/harbor)

## Environment Forwarding

Harbor delivers values into the task environment. NeMo Fabric forwards values from its task-side process to the adapter. Listing a variable in `environment.env_names` does not deliver it from the Harbor host to the task.

The existing `FabricAgent` bridge follows this flow for `fabric_environment_env`:

1. The bridge resolves host-variable references, such as `{"GITHUB_TOKEN": "${GITHUB_TOKEN}"}`, and adds the values to Harbor's managed `extra_env`.
2. The retained run specification contains only the names in its `environment_env_names` payload field.
3. Harbor supplies the values to the task runner's execution environment.
4. The task runner looks up the names and inserts the values into `config.environment.env` before calling NeMo Fabric.

`environment_env_names` is Harbor's existing transport field. `environment.env_names` is the core NeMo Fabric forwarding field described in [Set Environment Values Or Forward Them By Name](../../sdk/python.mdx#set-environment-values-or-forward-them-by-name). This addition does not migrate the Harbor bridge to the core field: Harbor's retained run specification contains names, but its runner still puts resolved values in `environment.env`, where values are serialized into the NeMo Fabric run plan.

Keep using Harbor's managed environment and redaction rules for credentials. Core `env_names` does not replace Harbor's secret delivery or redaction.

## Trial Identity In Run Records

Set `fabric_record=True` on `FabricAgent` to write a NeMo Fabric run record for
each agent run in a trial (one per step on a multi-step trial) under the
bridge's artifact root. It is off by default, and without
it the bridge sends the same request as before. With it on, the bridge reads
the trial's `lock.json` and `config.json`, which Harbor writes to the trial
folder before the agent starts, and adds these keys to the request context:

| Key | Source |
| --- | --- |
| `task_id` | The task name in `lock.json`: `org/name` for a registry task, and the task folder's name for a git or local task |
| `task_revision` | Harbor's content digest of the task (`sha256:...`) in `lock.json`, for every task kind |
| `harbor_trial_name` | The trial's `trial_name` in `config.json` |
| `step` | On a multi-step trial only (Harbor creates the trial's `steps` folder), the bridge's run count in the trial: 1 for the first step, 2 for the second, and so on |

The record's start line keeps them with `harbor_session_id` and
`harbor_context_id`. NeMo Fabric forwards these keys to the adapter, as it
forwards every request context key; no first-party adapter reads them. Harbor
runs each attempt as its own trial and gives the trial no attempt index, so the
bridge sets no `attempt`. Group a task's attempts by `task_id` and
`task_revision`. A missing or unreadable `lock.json` or `config.json`, or one
that does not hold a JSON object, adds none of its keys, and the run goes on.
Otherwise the bridge copies each field in the table that is a nonempty string on
its own, and does not check the file against Harbor's lock or config model.

On the host, each record is at
`<trial>/agent/fabric-artifacts/<config name>/.fabric/<runtime_id>/<invocation_id>/run-record.jsonl`,
where the config name is `harbor-` followed by the last part of the adapter
ID, such as `harbor-hermes`. On a multi-step trial, Harbor moves or copies the
agent folder's contents into `<trial>/steps/<step>/agent/` after each step, so
each step's records are there.

`fabric_record=True` needs a NeMo Fabric version with `runtime.record` in the
trial environment. With the first-party adapters, an older `fabric_package`
rejects the config.
